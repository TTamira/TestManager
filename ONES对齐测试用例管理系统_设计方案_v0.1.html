0结论摘要

一句话结论：技术上可行，最大风险点在 XMind 导入的「节点语义识别」——XMind 本身没有"用例"这个概念，必须靠约定（前缀、图标、备注、层级）反推。方案的核心是把这套约定做成可切换的多套识别模式 + 可视化预览纠错，而不是写死一套解析规则。

四条关键判断

  1. 对齐 ONES 是"数据模型对齐"，不是"功能全量复刻"。 ONES 的用例库 → 模块树 → 用例 → 步骤 这条主干非常清晰，直接照搬即可获得 80% 价值；需求追溯、权限、报告属于加分项，可在后续里程碑补齐。
  2. 必须做"先预览、后落库"。 XMind 是自由画布，脏数据是常态（空分组、孤立要点、步骤层级错位）。一次性静默导入会产生大量垃圾用例，且难以回滚。导入向导必须先给出结构化预览和逐节点问题标注。
  3. 建议 Python（FastAPI）技术栈。 XMind 解析生态在 Python 侧最成熟，且能直接复用你现有的 Python 环境；前端用 React + Ant Design，其 Tree / Table / Drawer 组件与 ONES 的观感几乎同构。
  4. 导入能力要做成"插件化规则"。 ONES 官方公开文档只明确 .opml / .xlsx，.xmind 与自定义字段映射见其产品更新说明；而云效、CODING 各有自己的一套 XMind 约定（tc: 前缀 vs + 分组 + 优先级图标）。规则可配置，才不会绑死在某一家。

1.3 测试计划与执行

  • 计划的组成：名称、经办人、测试阶段、关联项目、关联迭代、权限；高级设置里可配「缺陷的事务类型」。
  • 计划状态：待办 / 进行中 / 已完成。
  • 执行：进入用例执行界面，按前置条件、步骤、预期结果判定通过与否，记录「测试结果 + 说明 + 附件」；支持批量「更改结果」。
  • 提缺陷：失败用例可对某个步骤或整个用例创建缺陷 / 关联已有缺陷，缺陷自动落到计划关联的项目与迭代。
  • 需求追溯矩阵：第一列默认"需求"（可配为其他事务类型），按计划关联的需求展开；用于查覆盖率与"需求 → 用例 → 结果 → 缺陷"的链路。
  • 字段配置：可强制"设置测试结果时必须填说明 / 附件"。

2.3 测试计划与执行

分三屏：计划列表 → 计划详情（用例 + 执行人 + 结果）→ 执行界面。

  • 计划列表：按状态（待办 / 进行中 / 已完成）分组，支持按关联项目、关联迭代分组；每张卡片显示进度条（已执行/总数、通过率）。注："待确认"计入"已执行"但不计入通过/不通过分母，单列统计。
  • 计划详情：用例列表可排序（ID / 名称 / 维护者 / 优先级 / 类型 / 执行人 / 结果）、可复杂筛选、可隐藏子模块用例；支持批量改执行人、批量改结果。
  • 执行界面：逐步骤打勾（步骤级结果），整例给结论：通过 / 不通过 / 阻塞 / 待确认（执行情况字段，四态为用户指定；另有系统内建的"未执行"初始态，不可手动选中）；备注与附件可选必填（跟随计划的字段配置）；失败时按钮：创建缺陷 / 关联已有缺陷，可选挂在某一步骤或整个用例。"不通过"与"阻塞"均可提缺陷；"待确认"不提缺陷，用于结果存疑（如环境问题、需求未明确的 Demo-only 项）暂缓判定。
  • 键盘流：J/K 切上下条，P/F/B/S 直接标记结果，执行大型回归时效率提升明显。
设计决策（增强，非 ONES 行为）：测试计划引用用例时记录用例版本号（快照）。这样用例库后续被修改，不会污染历史执行结果的判定依据。ONES 未明确这一点，我们按更严谨的方式做，并在 UI 上标注"该用例在计划创建后已被修改"。

2.4 需求追溯矩阵

行 = 需求（从本地轻量「工作项」表读取，字段：编号 / 标题 / 类型 / 状态），列分组 = 用例 / 最新结果 / 关联缺陷。单元格点击直接跳到用例详情。该页面回答两个问题：哪些需求一条用例都没有、哪些需求只有浅层成功路径用例。

3XMind 导入引擎设计（核心模块）

3.1 先搞清楚 .xmind 到底是什么

.xmind 本质是一个 ZIP 包。把后缀改成 .zip 就能解开。内部结构随版本不同而不同，这是实现时的第一个坑：

版本关键文件陷阱
XMIND 8 及更早（legacy） content.xml 数据在 XML 里，用 xml.etree 或 lxml 解析
XMind 2020+ / Zen / 2026 content.json（真数据）
+ content.xml（占位）		 content.xml 里只有一句警告文本，不是数据。只读 content.xml 的解析器会"成功返回空导图"——这是最隐蔽的失败模式，必须显式检测。
通用附加物 resources/、metadata.json、manifest.json 图片、贴纸、附件都在 resources 下；content.json 是画布（sheet）数组，多画布必须显式处理
必须实现的兼容策略：优先读 content.json，不存在再回退 content.xml；并对"content.xml 仅含警告 / 无 rootTopic"的情况抛出明确错误，绝不静默产出 0 条用例。

3.2 节点语义：XMind 没有"用例"概念

这是整个方案最需要设计的地方。.xmind 里只有一棵主题树，没有"用例 / 模块 / 步骤"的类型信息，只能靠约定反推。业界已形成两套主流约定，我们的做法是两套都支持 + 一套纯层级兜底：

模式识别依据映射规则
M1 · 前缀声明
云效风格		 节点标题前缀 pc: xxx → 前置条件（必须是用例子节点）
tc: 标题 → 测试用例
tc-P1: 标题 → 用例，等级 P1
tc-P2-性能测试: 标题 → 等级 P2 + 类型"性能测试"
其余节点 → 分组（模块）
用例的子节点 → 步骤；步骤的子节点 → 预期结果
M2 · 标记驱动
CODING 风格		 XMind 原生优先级图标 + 备注 + + 前缀 + 开头的节点 → 分组；
分组下第一个非 + 节点 → 用例标题（后续同级节点为下一条用例）
标题上的优先级图标：priority-1→P0，2→P1，3→P2，≥4→P3
标题节点的备注（notes） → 前置条件
无子节点 → 文本型用例；有子节点 → 步骤型（步骤的子节点 = 预期结果，多个则合并）
M3 · 层级推导
兜底		 纯结构，零标记 根节点 = 画布标题（丢弃）
中间层 → 模块路径
叶节点 → 用例；提供参数「倒数第 N 层为用例」应对"分组下还有子分组"的情况
默认优先级 = 配置的默认值（如 P2）
为什么必须做成可切换：ONES 官方公开文档明确的用例库导入只有 .xlsx / .opml，.xmind 与"自定义导入字段"出现在其产品更新说明里，但公开文档未给出完整的节点约定规范。与其赌一套，不如做成规则可插拔——后续拿到真实 ONES 模板样例，只需新增一个规则实现，不动核心链路。

import json, zipfile
import xml.etree.ElementTree as ET

def read_xmind(path) -> tuple[list[dict], str]:
    """跨版本读取 XMind，返回 (画布列表, 格式标记)。"""
    with zipfile.ZipFile(path) as z:
        names = set(z.namelist())

        # 1) 新版优先：content.json
        if "content.json" in names:
            sheets = json.loads(z.read("content.json").decode("utf-8"))
            if not isinstance(sheets, list) or not sheets:
                raise ValueError("content.json 解析结果为空，文件可能损坏")
            out = []
            for s in sheets:
                out.append({
                    "title": s.get("title", ""),
                    "root":  s.get("rootTopic") or {},
                    # 浮动主题必须一并处理，否则用例会"莫名少几条"
                    "detached": s.get("detachedTopics") or [],
                })
            return out, "json"

        # 2) 回退老版：content.xml
        if "content.xml" in names:
            root = ET.fromstring(z.read("content.xml"))
            sheets = []
            for sheet in root.iter("sheet"):
                topic = sheet.find("topic")
                if topic is None:
                    continue
                sheets.append({
                    "title": sheet.get("title", ""),
                    "root":  _xml_topic_to_dict(topic),
                    "detached": [],
                })
            if not sheets:
                raise ValueError("content.xml 中未找到有效画布（可能是新版文件的占位文件）")
            return sheets, "xml"

    raise ValueError("不是有效的 .xmind 文件：缺少 content.json / content.xml")


def markers_of(topic: dict) -> list[str]:
    """新版优先级/图标：topic.markers = [{"markerId": "priority-1"}, ...]"""
    return [m.get("markerId", "") for m in (topic.get("markers") or [])]


PRIORITY_MAP = {"priority-1": "P0", "priority-2": "P1", "priority-3": "P2"}
# 与 ONES / CODING 的约定一致：图标 1/2/3 对应 P0/P1/P2，≥4 或缺失 → P3（或取默认值）

def priority_of(topic: dict, default: str = "P3") -> str:
    for mk in markers_of(topic):
        if mk in PRIORITY_MAP:
            return PRIORITY_MAP[mk]
        if mk.startswith("priority-"):
            return "P3"          # priority-4 ~ 9 一律 P3
    return default


def attached_children(topic: dict) -> list[dict]:
    return ((topic.get("children") or {}).get("attached") or [])


def notes_plain(topic: dict) -> str:
    """优先取 notes.plain；只有 html 时剥标签后作为兜底。"""
    notes = topic.get("notes") or {}
    plain = (notes.get("plain") or {}).get("content")
    if plain:
        return plain.strip()

工程注意（踩坑清单）：
  1. 只读 content.xml 的库在新版文件上会返回"空导图"而非报错 → 必须显式探测。
  2. 浮动主题（detachedTopics）不处理会丢用例。
  3. 多画布：必须在向导里让用户选择画布（或勾选合并），不能默认取第一个。
  4. 备注里的 notes.html 是 XHTML 片段，含命名空间，直接当纯文本用会带标签。
  5. 节点标题可能含零宽字符/全角空格，会导致"看起来同名"的用例去重失败 → 入库前统一 normalize。

3.5 导入向导（4 步，先预览后落库）

冲突策略（第 ③ 步，用户显式选择）

策略行为适用场景
全部新建不比对，全部插入新用例首次导入
跳过已存在默认按指纹（模块路径 + 归一化标题）判重，已存在的跳过并记入报告重复导入同一文件（对齐 ONES 的"同名不覆盖"行为）
更新已存在覆盖已存在用例的字段与步骤，并生成新版本快照XMind 修完后重新同步
仅追加步骤保留原用例字段，把新步骤追加到步骤末尾补充测试步骤

3.6 校验规则（V = 拦截级，W = 告警级）

级别规则处理
V空分组（分组下无任何用例）拒绝落库，提示删除该分组或补用例
V用例标题为空 / 仅空白字符拒绝，标注节点路径
V步骤层级错位（步骤下出现了"步骤的兄弟"而非预期结果）拒绝并提示预期结构
W步骤数 > 20截断到 20，报告标注被忽略的节点
W预期结果合并后 > 200 字符截断并告警
W模块层级 > 10 级告警；超出部分压缩为一级或提示扁平化
W层级过深但全无 tc: 标记（疑似用 M1 模式解析 M3 文件）告警并推荐切换识别模式——这是最常见的"识别模式选错"信号
W单次导入 > 500 条用例提示分批，或走后台任务队列
W同名用例重复（同一模块路径下）按冲突策略处理并计数

3.7 幂等设计

  • 每次导入生成 import_batch 记录（文件指纹 SHA-256、识别模式、目标库、操作人、计数）。
  • 每条用例保存 source_node_id + source_file_hash；同一文件重复导入时按指纹快速判重。
  • 导入批次支持整批回滚：删除该批次新建的用例（软删进回收站），已更新用例按版本快照还原。
  • 大体量导入拆分为事务小批，任意一批失败不影响已成功批次，报告中可定位到具体批次重试。

3.8 反向导出（可选，建议做）

用例库 → .xmind：按 模块路径 → 用例（标题带 tc-前缀）→ 步骤 → 预期结果 生成 content.json 并打包为 zip。价值在于：XMind 是测试人员最顺手的批量编辑界面——把 XMind 当"编辑器"，本系统当"数据库"，形成"导出改 → 导入回"的闭环。工程量不大（就是 3.4 节的逆过程），建议纳入 M2。

4.2 三个关键设计决策

  1. 统一字段模型而不是给每个字段一列。 自定义字段用宽表会失控；采用 field + case_field_value（EAV）承载自定义字段，系统高频字段（title / priority / module / maintainer）保留为真实列以保证查询性能。这是"性能与灵活性"的折中。
  2. 模块树用物化路径 + 排序号。 module.path（如 /12/45/78/）让"查某模块含子模块的全部用例"退化为字符串前缀查询，避免递归 CTE。sort_order 用稀疏步长（1000）支撑拖拽插入时不必全表重排。
  3. 执行结果与用例本体分离。 用例库是"长期资产"，执行结果属于"某一次计划"。两者不同生命周期，混在一张表会导致历史结果被用例修改污染——这也是为什么要有 case_snapshot_version。

5技术选型

方案 A · Python 后端 + React 前端 推荐

  • 后端：FastAPI + SQLAlchemy 2.0 + Alembic
  • 数据库：SQLite（单机）→ PostgreSQL（多人）无缝切换
  • 前端：Vite + React + TypeScript + Ant Design
  • XMind/OPML 解析：Python 原生 zipfile + json / lxml
  • Excel：openpyxl

优点：XMind 解析生态成熟；可复用你现有 Python 环境；AntD 的 Tree/Table/Drawer 与 ONES 观感高度同构；单机一键启动，后续可平滑上多用户。
代价：前后端两个进程，部署比单体稍复杂。

方案 B · Next.js 全栈单体

  • Next.js + Prisma + SQLite/PostgreSQL
  • 解析用 xmind npm 或自研（zip + JSON 解析 Node 也能做）
  • 一份代码、一处部署

优点：工程结构简单，API 与页面同仓同构，类型可端到端共享。
代价：Node 侧 XMind 解析库在新版 content.json 上的兼容性不如 Python 侧社区实践充分，可能需要自己补坑；且与你现有 Python 技术栈割裂。

推荐理由（方案 A）：本项目的技术难点集中在"XMind 跨版本解析 + 结构识别 + 预览纠错"，这部分 Python 侧的社区实践最充分（content.json / content.xml 双通道、marker/notes 提取都有成熟先例）。把风险耗在解析上是划算的，UI 与数据库都属常规工程。

部署形态

  • 单机自用：python -m app 起后端 + 静态前端产物，浏览器访问 localhost，数据落 SQLite 文件。可做成 Windows 一键启动脚本。
  • 团队共用：Docker Compose（后端 + PostgreSQL + Nginx），加登录与库级权限。

6里程碑与交付物

按"每个阶段都能独立用起来"切分，而不是按技术层次切分。工作量用相对量级标注（S < M < L），具体排期待技术栈确认后再定。

阶段主题交付物量级验收标准
M0骨架可用 用例库管理 + 模块树（拖拽/计数/删除不删用例）+ 用例 CRUD + 字段定义与字段配置 + 回收站 L 能手工把 30 条用例按模块树录完并正常检索
M1XMind 导入核心 跨版本解析器 + M1/M2/M3 三种识别模式 + 4 步导入向导 + 校验规则 + 幂等与整批回滚 + 导入报告 L 一份真实 XMind 用例文件导入后，结构、等级、前置条件、步骤/预期 100% 正确；重复导入不产生重复用例
M2计划与执行 测试计划 CRUD + 关联用例 + 执行人分配 + 执行界面（步骤级打勾、结果、备注、附件）+ 批量改结果 + 失败提缺陷 + 用例→XMind 反导出 L 一条完整回归计划能跑完并产出结果统计
M3追溯与报告 需求追溯矩阵 + 测试报告（进度 / 通过率 / 缺陷分布 / 按模块·执行人）+ xlsx / opml 导入导出 M 能从需求出发查到用例与最新结果，并导出全字段
M4协作与对接 登录与库级权限、审计日志、REST API、导入规则插件化（新增规则只加实现不动核心）、ONES 迁移脚本 M 多人可分权使用；可通过 API 与外部系统交互
建议的推进顺序：M1 优先于 M0 的完整度。先把"导入 30 秒出结果"这条链路打通（哪怕 UI 粗糙），用它把你的真实 XMind 用例库灌进去，再回头按真实数据结构打磨 M0 的字段与交互。理由：本方案最大的未知是"你的 XMind 实际长什么样"，先用真实数据把这个不确定性消掉，后续设计才不会是纸上谈兵。

7待确认清单

以下问题会实质影响数据模型与工程量，需要在动手写代码前确认。我按影响程度排序：

#问题为什么关键 / 影响面
1 能否提供一份真实的 .xmind 用例文件（以及 ONES 导出/模板样例，如果有）？ 最高优先级。它决定识别模式以哪一套为准、层级深度、优先级是用图标还是前缀、前置条件放备注还是 pc: 节点。拿到文件我可以先写一个解析脚本跑一遍，把识别规则调准，再写系统——这一步能省掉大量返工。
2 使用场景是单机自用还是团队多人？ 决定是否需要登录、用户体系、库级权限、并发写入处理。单机版可以把 M4 砍掉，工程量显著下降。
3 与 ONES 的关系：只要结构对齐便于日后迁移，还是要做数据往返（导出 ONES 可直接再导入的格式）？ 前者只需字段命名与层级对齐；后者需要额外实现 ONES 的导入模板格式，并在 M1 增加"ONEs 兼容导出"。
4 是否保留禅道标准 10 列 xlsx 的导入导出？ 你现有工作流是"禅道 10 列 xlsx"。若保留，系统需内置这套映射，等于多一个导入适配器；好处是新工具能立刻接管现有资产，不用从零录。
5 技术栈确认：Python(FastAPI) + React 是否可接受？ 决定实现方式与你后续自己维护的难度。
6 是否需要用例评审流（提交评审 → 通过/驳回 → 状态流转）？ MVP 我按"版本历史 + 状态标记"的轻量方案设计。若需要正式评审流程，M0 要加状态机与评审记录表。
7 需求/缺陷是否需要与外部系统（ONES / 禅道 / Jira）打通？ 若只做本地轻量引用（维护编号+标题+链接），M3 很轻；若要做 API 双向同步，需单独评估对方开放平台能力。
8 是否需要 XMind 反向导出（用例库 → .xmind）？ 工程量不大且实用（把 XMind 当批量编辑器），建议做，但需确认。
本方案中的假设（若与实际不符请指出）：
  1. 优先级 semantics 采用 P0 冒烟 → P3 低频，与 ONES 文档一致。
  2. XMind 优先级图标 priority-1/2/3 分别映射 P0/P1/P2，≥4 映射 P3（与 CODING 约定一致）。
  3. "步骤型用例"的每个步骤最多对应一条预期结果；多条预期结果按合并处理（对齐云效的实现）。
  4. 模块树层级上限取 10 级（ONES 系产品普遍在 8–12 级之间）。
  5. 用例 ID 形如 TC-0001，按库内自增。
  6. 执行结果枚举（执行情况，用户已确认）：通过 / 不通过 / 阻塞 / 待确认 四态 + 系统内建的"未执行"初始态。不设"跳过"态——"跳过"的场景由"待确认"覆盖。
