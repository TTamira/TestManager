0结论摘要

一句话结论：技术上可行，最大风险点在 XMind 导入的「节点语义识别」——XMind 本身没有"用例"这个概念，必须靠约定（前缀、图标、备注、层级）反推。方案的核心是把这套约定做成可切换的多套识别模式 + 可视化预览纠错，而不是写死一套解析规则。

四条关键判断

  1. 对齐 ONES 是"数据模型对齐"，不是"功能全量复刻"。 ONES 的用例库 → 模块树 → 用例 → 步骤 这条主干非常清晰，直接照搬即可获得 80% 价值；需求追溯、权限、报告属于加分项，可在后续里程碑补齐。
  2. 必须做"先预览、后落库"。 XMind 是自由画布，脏数据是常态（空分组、孤立要点、步骤层级错位）。一次性静默导入会产生大量垃圾用例，且难以回滚。导入向导必须先给出结构化预览和逐节点问题标注。
  3. 建议 Python（FastAPI）技术栈。 XMind 解析生态在 Python 侧最成熟，且能直接复用你现有的 Python 环境；前端用 React + Ant Design，其 Tree / Table / Drawer 组件与 ONES 的观感几乎同构。
  4. 导入能力要做成"插件化规则"。 ONES 官方公开文档只明确 .opml / .xlsx，.xmind 与自定义字段映射见其产品更新说明；而云效、CODING 各有自己的一套 XMind 约定（tc: 前缀 vs + 分组 + 优先级图标）。规则可配置，才不会绑死在某一家。
v0.2 已落地（2026-09-29 用户确认）：基于用户提供的真实样例 法律agent业务工作台.xmind 验证了导入识别规则；确认用例内容可由 AI 代写（默认 DeepSeek，可切 GPT）；测试计划支持用户自建 + 从用例库引用导入 + 多轮并存；用例库/模块树/用例均支持系统内手动增删改；评审流简化为"待修改"标记；执行情况四态 = 通过/不通过/阻塞/待确认 + 系统"未执行"初始态。详见第 7 章确认结论。

1.2 字段体系：两层结构（这是 ONES 设计里最值得抄的一点）

ONES 把"字段"拆成了两层，解耦了「系统有哪些属性」和「某个用例库显示哪些属性」：

概念说明对齐要点
测试用例字段
Field		 原子字段定义（名称 + 类型）。系统字段不可编辑，仅「优先级」「测试用例类型」例外，可改选项。 要有 scope = system | custom 标记，系统字段禁止删除/改名。
测试用例字段配置
FieldConfig		 由多个字段组成的集合，决定"使用该配置的用例库显示哪些字段"；可设默认值与必填。不同用例库可用不同配置。 库 ↔ 配置 是 1:N；配置被库引用时禁止删除。

1.3 测试计划与执行

  • 计划的组成：名称、经办人、测试阶段、关联项目、关联迭代、权限；高级设置里可配「缺陷的事务类型」。
  • 计划状态：待办 / 进行中 / 已完成。
  • 执行：进入用例执行界面，按前置条件、步骤、预期结果判定通过与否，记录「测试结果 + 说明 + 附件」；支持批量「更改结果」。
  • 提缺陷：失败用例可对某个步骤或整个用例创建缺陷 / 关联已有缺陷，缺陷自动落到计划关联的项目与迭代。
  • 需求追溯矩阵：第一列默认"需求"（可配为其他事务类型），按计划关联的需求展开；用于查覆盖率与"需求 → 用例 → 结果 → 缺陷"的链路。
  • 字段配置：可强制"设置测试结果时必须填说明 / 附件"。

1.4 其他与对齐相关的机制

机制行为（需在设计中复刻）

导入Excel(.xlsx)、思维导图(.opml)；产品更新说明确认支持 .xmind 及自定义导入字段
导出全部 / 仅选中，导出用例全字段

1.5 对齐边界：明确"抄什么"和"不抄什么"

✅ 对齐（MVP 必做）

  • 用例库 / 模块树（拖拽、计数、删除不删用例）
  • 字段定义 + 字段配置两层体系
  • 用例属性命名与 ID 规则
  • 优先级 P0–P3 语义
  • 文本型 / 步骤型 两种用例形态
  • 回收站与恢复
  • 平铺 / 树状视图、显示子模块开关
  • 导入 xlsx / xmind / opml，导出全字段

⏸ 暂不对齐（后置，避免过度设计）

  • 多租户、SSO、组织级权限矩阵
  • 与需求/迭代/缺陷系统的双向实时同步
  • Wiki 页面关联
  • CI/CD 与自动化测试集成
  • 自定义测试报告模板引擎
  • 完整 ONES 评审流（提交→通过/驳回状态机）；本系统改用轻量 review_status：待评审 / 已通过 / 待修改（用户可标记"待修改"）

2.2 用例库主界面（三栏 + 双层工具栏）

  • 左栏（模块树，280px 可拖宽）：模块树 + 每节点显示「所含用例总数（含子模块）」；右键菜单：创建子模块 / 重命名 / 删除 / 复制模块路径；顶部有"定位到当前模块"与筛选框。
  • 右栏（用例列表）：默认列 = 复选框、用例 ID、名称、维护者、优先级、类型、执行人、测试结果、操作。
  • 工具栏第一行：+ 创建用例、导入用例（xlsx / xmind / opml）、导出用例、筛选器、列设置。
  • 工具栏第二行：视图切换（平铺 / 树状）、显示子模块用例开关、批量操作条（移动 / 复制 / 删除 / 关联计划 / 修改字段）。
  • 交互一致性：点行展开详情抽屉，URL 同步 ?case=TC-0012，方便直接分享/收藏某条用例。

2.3 测试计划与执行（计划由用户自建、可多轮并存）

测试不是只有一轮。系统支持用户自建多个测试计划（如"冒烟测试""功能测试""回归测试"），每个计划从用例库"引用导入"用例（按模块、按优先级筛选，例如只导 P0，或导 P0–P3）。导入是引用而非复制：同一用例可进入多个计划，各计划各自记录执行结果、互不影响。分三屏：计划列表 → 计划详情（用例 + 执行人 + 结果）→ 执行界面。

  • 计划列表：用户可新建/重命名/删除计划；按状态（待办 / 进行中 / 已完成）分组；每张卡片显示进度条（已执行/总数、通过率），并提供"从用例库导入"入口。注："待确认"计入"已执行"但不计入通过/不通过分母，单列统计。
  • 计划详情：用例列表可排序（ID / 名称 / 维护者 / 优先级 / 类型 / 执行人 / 结果）、可复杂筛选、可隐藏子模块用例；支持批量改执行人、批量改结果。
  • 执行界面：逐步骤打勾（步骤级结果），整例给结论：通过 / 不通过 / 阻塞 / 待确认（执行情况字段，四态为用户指定；另有系统内建的"未执行"初始态，不可手动选中）；备注与附件可选必填（跟随计划的字段配置）；失败时按钮：创建缺陷 / 关联已有缺陷，可选挂在某一步骤或整个用例。"不通过"与"阻塞"均可提缺陷；"待确认"不提缺陷，用于结果存疑（如环境问题、需求未明确的 Demo-only 项）暂缓判定。
  • 键盘流：J/K 切上下条，P/F/B/S 直接标记结果，执行大型回归时效率提升明显。
设计决策（增强，非 ONES 行为）：测试计划引用用例时记录用例版本号（快照）。这样用例库后续被修改，不会污染历史执行结果的判定依据。ONES 未明确这一点，我们按更严谨的方式做，并在 UI 上标注"该用例在计划创建后已被修改"。

2.4 用例内容录入：表单是统一终点（含 AI 辅助编写）

用例内容的生产者可能是你打字，也可能是 AI 产出文本。两者不是两条平行线，而是汇聚到同一个表单：

  • XMind 导入：负责"骨架"（模块/用例名），内容由解析器填入表单。
  • 导入文本（起步即支持，零对接）：你把 AI（DeepSeek 等）或自己按《内容约定格式》写好的文本粘进系统，系统解析后落入表单。无需任何 API key。
  • 手动表单：直接在系统表单里逐字段打字（传统录入，连解析都省了）。

无论内容谁生产、什么格式，最后都进同一个表单，由你复核确认后保存。AI 不"填"表单，而是产出结构化文本 → 系统解析 → 文本变成表单里的字段 → 你确认保存。

内容约定格式（AI 与人共用，系统只认这一种结构）

模块: 登录功能
用例: 正确账号密码登录
优先级: P0
前置条件: 已注册且未登录
步骤:
1. 打开登录页
   预期: 显示账号、密码输入框及登录按钮
2. 输入正确的手机号和密码
   预期: 输入框正常回显
3. 点击登录
最终预期: 跳转首页，右上角显示用户昵称

该格式与 XMind 笔记的三段式（前置条件 / 用例步骤 / 预期结果）完全一致，故XMind 笔记解析与文本导入共用同一解析器。其中每步骤可带"预期"（内联预期，可选），用例级"最终预期"为可选的整体核对点——覆盖"大部分情况最后一步才有预期、有时中间步骤也要写预期"的真实写法。

AI 客户端（预留，非现在接入）

DeepSeek 与 OpenAI(GPT) 均提供 OpenAI 兼容的 chat/completions API。系统预留一个可切换的 provider-agnostic 客户端（改 base_url / api_key / model 三值即可切换），默认指向 DeepSeek，后续可切 GPT。系统内的"AI 帮我写"按钮（直接调 API）列为后期增强，起步阶段用"导入文本"兜底，届时接入需单独审批。

2.5 需求追溯矩阵

行 = 需求（从本地轻量「工作项」表读取，字段：编号 / 标题 / 类型 / 状态），列分组 = 用例 / 最新结果 / 关联缺陷。单元格点击直接跳到用例详情。该页面回答两个问题：哪些需求一条用例都没有、哪些需求只有浅层成功路径用例。

2.6 UI 主题（三套独立预设：浅灰 / 浅粉 / 黑）

界面提供三套互相独立的色预设，用户可在设置里一键切换并本地持久化；三套不混合、不叠加，各是一套完整的 token 集合：

预设页面底色强调色（主按钮 / 选中）文字对比
浅灰色（默认）冷调浅灰 #EFF1F5，卡片 #FFFFFF沉静蓝灰 #5F7FA6（中性、不抢眼）正文 #4C4F69，约 8.8:1 达标
浅粉色柔粉底 #F8EAF0，卡片 #FFFFFF / 粉白玫瑰粉 #B83B6B（深粉，保证可读）正文 #5A2A3E，约 7.5:1 达标
黑色近黑 #1E1E1E，卡片 #2A2A2A亮粉 #F5C2E7（深色面用蓝灰而非纯黑，层次更柔）正文 #E6E6E8，约 12:1 达标

设计约束：① 三套都是"弱对比氛围 + 高对比文字"——区块底色可柔，正文与关键文字必须 ≥ WCAG AA（4.5:1）；② 强调色文字必须加深 / 反白，不得浅底配浅字；③ 实现基于 Ant Design v5 theme token + ConfigProvider，每套预设即一组 token 值，切换零成本、无需重写组件；④ 优先做这三套，自定义主题列为保留项。

3XMind 导入引擎设计（核心模块）

3.1 先搞清楚 .xmind 到底是什么

.xmind 本质是一个 ZIP 包。把后缀改成 .zip 就能解开。内部结构随版本不同而不同，这是实现时的第一个坑：

版本关键文件陷阱
XMIND 8 及更早（legacy） content.xml 数据在 XML 里，用 xml.etree 或 lxml 解析
XMind 2020+ / Zen / 2026 content.json（真数据）
+ content.xml（占位）		 content.xml 里只有一句警告文本，不是数据。只读 content.xml 的解析器会"成功返回空导图"——这是最隐蔽的失败模式，必须显式检测。
通用附加物 resources/、metadata.json、manifest.json 图片、贴纸、附件都在 resources 下；content.json 是画布（sheet）数组，多画布必须显式处理
必须实现的兼容策略：优先读 content.json，不存在再回退 content.xml；并对"content.xml 仅含警告 / 无 rootTopic"的情况抛出明确错误，绝不静默产出 0 条用例。

3.2 节点语义：XMind 没有"用例"概念

这是整个方案最需要设计的地方。.xmind 里只有一棵主题树，没有"用例 / 模块 / 步骤"的类型信息，只能靠约定反推。业界已形成两套主流约定，我们的做法是两套都支持 + 一套纯层级兜底：

模式识别依据映射规则
M1 · 前缀声明
云效风格		 节点标题前缀 pc: xxx → 前置条件（必须是用例子节点）
tc: 标题 → 测试用例
tc-P1: 标题 → 用例，等级 P1
tc-P2-性能测试: 标题 → 等级 P2 + 类型"性能测试"
其余节点 → 分组（模块）
用例的子节点 → 步骤；步骤的子节点 → 预期结果
M2 · 标记驱动
CODING 风格		 XMind 原生优先级图标 + 备注 + + 前缀 + 开头的节点 → 分组；
分组下第一个非 + 节点 → 用例标题（后续同级节点为下一条用例）
标题上的优先级图标：priority-1→P0，2→P1，3→P2，≥4→P3
标题节点的备注（notes） → 前置条件
无子节点 → 文本型用例；有子节点 → 步骤型（步骤的子节点 = 预期结果，多个则合并）
M3 · 层级推导
兜底		 纯结构，零标记 根节点 = 画布标题（丢弃）
中间层 → 模块路径
叶节点 → 用例；提供参数「倒数第 N 层为用例」应对"分组下还有子分组"的情况
默认优先级 = 配置的默认值（如 P2）

3.2.1 基于真实样例的默认识别规则（2026-09-29 用 法律agent业务工作台.xmind 验证）

用户实际使用方式极其简洁，且恰好与上面的"层级推导"一致，故将其定为默认识别模式：

XMind 元素映射为
中心主题（d0）用例库名（如 业务工作台）
所有非叶子节点功能模块树（功能地图）；至多 4 级（一级模块 → 子模块 → …）
叶子节点（无子节点）测试用例，标题 = 用例名
叶子节点的笔记用例内容，按三段式「前置条件 / 用例步骤 / 预期结果」解析
优先级范围铁律（2026-09-29 用户确认）：优先级是用例（末端叶子）的属性，骨架不携带优先级——中心主题与所有模块节点（功能地图）都不写优先级，即使出现也直接忽略。优先级 Token（P0–P3）只解析末端叶子的两种写法：① 标题前缀 P0 · 用例名；② 笔记专行 优先级: P0。多源优先级：标题前缀 > 笔记行 > 内建标记(可选) > 未设；叶子未写则导入为"未设"，在表单补。该约定与《内容约定格式》的 优先级: P0 字段完全自洽，人 / AI / 系统三端对齐。
两个实测缺口（已在规则中处理）：
  • 优先级未编码：真实文件全文件 0 markers / 0 labels。规则支持在笔记里加可选行 优先级: P0；缺省则导入为"未设"，在表单补。
  • 半成品：34 个末端仅 11 个有笔记。空笔记的末端也作为"用例但内容待补"导入进库，供用户在系统内后续补全，而不是跳过。
为什么做成可切换：ONES 官方公开文档明确的用例库导入只有 .xlsx / .opml，.xmind 与"自定义导入字段"出现在其产品更新说明里，但公开文档未给出完整的节点约定规范。与之并列的 M1/M2 模式（云效 / CODING 约定）保留为可插拔选项，后续拿到真实 ONES 模板样例，只需新增一个规则实现，不动核心链路。

import json, zipfile
import xml.etree.ElementTree as ET

def read_xmind(path) -> tuple[list[dict], str]:
    """跨版本读取 XMind，返回 (画布列表, 格式标记)。"""
    with zipfile.ZipFile(path) as z:
        names = set(z.namelist())

        # 1) 新版优先：content.json
        if "content.json" in names:
            sheets = json.loads(z.read("content.json").decode("utf-8"))
            if not isinstance(sheets, list) or not sheets:
                raise ValueError("content.json 解析结果为空，文件可能损坏")
            out = []
            for s in sheets:
                out.append({
                    "title": s.get("title", ""),
                    "root":  s.get("rootTopic") or {},
                    # 浮动主题必须一并处理，否则用例会"莫名少几条"
                    "detached": s.get("detachedTopics") or [],
                })
            return out, "json"

        # 2) 回退老版：content.xml
        if "content.xml" in names:
            root = ET.fromstring(z.read("content.xml"))
            sheets = []
            for sheet in root.iter("sheet"):
                topic = sheet.find("topic")
                if topic is None:
                    continue
                sheets.append({
                    "title": sheet.get("title", ""),
                    "root":  _xml_topic_to_dict(topic),
                    "detached": [],
                })
            if not sheets:
                raise ValueError("content.xml 中未找到有效画布（可能是新版文件的占位文件）")
            return sheets, "xml"

    raise ValueError("不是有效的 .xmind 文件：缺少 content.json / content.xml")


def markers_of(topic: dict) -> list[str]:
    """新版优先级/图标：topic.markers = [{"markerId": "priority-1"}, ...]"""
    return [m.get("markerId", "") for m in (topic.get("markers") or [])]


PRIORITY_MAP = {"priority-1": "P0", "priority-2": "P1", "priority-3": "P2"}
# 与 ONES / CODING 的约定一致：图标 1/2/3 对应 P0/P1/P2，≥4 或缺失 → P3（或取默认值）

def priority_of(topic: dict, default: str = "P3") -> str:
    for mk in markers_of(topic):
        if mk in PRIORITY_MAP:
            return PRIORITY_MAP[mk]
        if mk.startswith("priority-"):
            return "P3"          # priority-4 ~ 9 一律 P3
    return default


def attached_children(topic: dict) -> list[dict]:
    return ((topic.get("children") or {}).get("attached") or [])


def notes_plain(topic: dict) -> str:
    """优先取 notes.plain；只有 html 时剥标签后作为兜底。"""
    notes = topic.get("notes") or {}
    plain = (notes.get("plain") or {}).get("content")
    if plain:
        return plain.strip()
    html = (notes.get("html") or {}).get("content") or ""
    return re.sub(r"<[^>]+>", "", html).strip()

3.4.1 步骤与预期配对规则（逐条内联预期 + 最终预期）

用户真实写法：大部分情况只有最后一步才有预期（整体预期），但有时中间某一步也要单独写预期。为此数据模型支持两者并存：每个步骤可带内联预期（可选），用例级另有一个最终预期（可选的整体核对点）。解析启发式（针对 XMind 的"步骤列表 + 预期列表"两段式）：

  • 预期仅 1 条且步骤 > 1 条 → 该预期为最终预期（最常见情形）；
  • 预期条数 == 步骤条数 → 逐条 1:1 内联配对；
  • 其余情形（1 < 预期数 < 步骤数，或预期数 > 步骤数）→ 前若干步骤内联配对，余下与整体预期交由导入向导第②步"结构预览纠错"闸门人工确认，绝不静默乱序落库。
工程注意（踩坑清单）：
  1. 只读 content.xml 的库在新版文件上会返回"空导图"而非报错 → 必须显式探测。
  2. 浮动主题（detachedTopics）不处理会丢用例。
  3. 多画布：必须在向导里让用户选择画布（或勾选合并），不能默认取第一个。
  4. 备注里的 notes.html 是 XHTML 片段，含命名空间，直接当纯文本用会带标签。
  5. 节点标题可能含零宽字符/全角空格，会导致"看起来同名"的用例去重失败 → 入库前统一 normalize。

3.5 导入向导（4 步，先预览后落库）

冲突策略（第 ③ 步，用户显式选择）

策略行为适用场景
全部新建不比对，全部插入新用例首次导入

更新已存在覆盖已存在用例的字段与步骤，并生成新版本快照XMind 修完后重新同步

3.6 校验规则（V = 拦截级，W = 告警级）

级别规则处理
V空分组（分组下无任何用例）拒绝落库，提示删除该分组或补用例
V用例标题为空 / 仅空白字符拒绝，标注节点路径
V步骤层级错位（步骤下出现了"步骤的兄弟"而非预期结果）拒绝并提示预期结构
W步骤数 > 20截断到 20，报告标注被忽略的节点
W预期结果合并后 > 200 字符截断并告警
W模块层级 > 10 级告警；超出部分压缩为一级或提示扁平化

W同名用例重复（同一模块路径下）按冲突策略处理并计数

3.7 幂等设计

  • 每次导入生成 import_batch 记录（文件指纹 SHA-256、识别模式、目标库、操作人、计数）。
  • 每条用例保存 source_node_id + source_file_hash；同一文件重复导入时按指纹快速判重。
  • 导入批次支持整批回滚：删除该批次新建的用例（软删进回收站），已更新用例按版本快照还原。
  • 大体量导入拆分为事务小批，任意一批失败不影响已成功批次，报告中可定位到具体批次重试。

3.8 反向导出（保留项，本期不做）

用例库 → .xmind：按 模块路径 → 用例（标题带 tc-前缀）→ 步骤 → 预期结果 生成 content.json 并打包为 zip。价值在于：XMind 是测试人员最顺手的批量编辑界面——把 XMind 当"编辑器"，本系统当"数据库"，形成"导出改 → 导入回"的闭环。工程量不大（就是 3.4 节的逆过程）。用户已确认本期不做，列为保留项，待实际使用后再评估是否启用。

4.2 三个关键设计决策

  1. 统一字段模型而不是给每个字段一列。 自定义字段用宽表会失控；采用 field + case_field_value（EAV）承载自定义字段，系统高频字段（title / priority / module / maintainer）保留为真实列以保证查询性能。这是"性能与灵活性"的折中。
  2. 模块树用物化路径 + 排序号。 module.path（如 /12/45/78/）让"查某模块含子模块的全部用例"退化为字符串前缀查询，避免递归 CTE。sort_order 用稀疏步长（1000）支撑拖拽插入时不必全表重排。
  3. 执行结果与用例本体分离。 用例库是"长期资产"，执行结果属于"某一次计划"。两者不同生命周期，混在一张表会导致历史结果被用例修改污染——这也是为什么要有 case_snapshot_version。

5技术选型

方案 A · Python 后端 + React 前端 推荐

  • 后端：FastAPI + SQLAlchemy 2.0 + Alembic
  • 数据库：PostgreSQL（用户已持有 pgAdmin4 作可视化管理，单机亦可运行 PG 服务）；不采用 SQLite，统一以 PG 为唯一存储
  • 前端：Vite + React + TypeScript + Ant Design
  • XMind/OPML 解析：Python 原生 zipfile + json / lxml
  • Excel：openpyxl

优点：XMind 解析生态成熟；可复用你现有 Python 环境；AntD 的 Tree/Table/Drawer 与 ONES 观感高度同构；单机一键启动，后续可平滑上多用户。
代价：前后端两个进程，部署比单体稍复杂。

方案 B · Next.js 全栈单体

  • Next.js + Prisma + SQLite/PostgreSQL
  • 解析用 xmind npm 或自研（zip + JSON 解析 Node 也能做）
  • 一份代码、一处部署

优点：工程结构简单，API 与页面同仓同构，类型可端到端共享。
代价：Node 侧 XMind 解析库在新版 content.json 上的兼容性不如 Python 侧社区实践充分，可能需要自己补坑；且与你现有 Python 技术栈割裂。

推荐理由（方案 A）：本项目的技术难点集中在"XMind 跨版本解析 + 结构识别 + 预览纠错"，这部分 Python 侧的社区实践最充分（content.json / content.xml 双通道、marker/notes 提取都有成熟先例）。把风险耗在解析上是划算的，UI 与数据库都属常规工程。

部署形态

  • 单机自用：python -m app 起后端 + 静态前端产物，浏览器访问 localhost，数据落本地 PostgreSQL 实例（可做成 Windows 一键启动脚本，自动拉起 PG 服务）。pgAdmin4 用于可视化查看与管理数据。
  • 团队共用：Docker Compose（后端 + PostgreSQL + Nginx），加登录与库级权限。

7确认结论（v0.2 已锁定）

以下决策已由用户在 2026-09-29 确认，作为 v0.2 设计基线，不再动摇：

#决策项结论
1真实 .xmind 样例已提供 法律agent业务工作台.xmind，并据此验证默认识别规则（中心主题=库名 / 非叶子=模块 / 叶子=用例 / 叶子笔记=三段式）。
2使用场景单机自用，无登录 / 权限 / 并发需求。
3与 ONES 关系仅结构对齐，不做数据往返（ONES 兼容导出列为保留项）。
4禅道 10 列 xlsx不保留，不做禅道导入导出。
5技术栈FastAPI + SQLAlchemy(PostgreSQL) + React/TS + Ant Design + Vite。
6用例评审流简化为轻量评审状态：待评审 / 已通过 / 待修改（用例可标记"待修改"）。
7外部系统打通不与 ONES / 禅道 / Jira 打通。
8XMind 反向导出本期不做，列为保留项。
9执行情况字段四态：通过 / 不通过 / 阻塞 / 待确认 + 系统"未执行"初始态；不设"跳过"；"待确认"单列统计。
10用例内容录入表单为统一终点；三路来源（XMind 导入 / 导入文本(AI或手写) / 手动表单）汇入；新增"导入文本"入口与《内容约定格式》；AI 默认 DeepSeek、可切 GPT，系统内"AI 帮我写"按钮列为后期增强。
11测试计划用户自建多个计划 + 从用例库引用导入用例（按模块/优先级筛选）+ 多轮并存；导入=引用非复制。
12系统内手动编辑用例库 / 模块树 / 用例均支持手动增删改（新建 / 重命名 / 拖拽排序 / 删除），XMind 导入只是灌入初始结构的手段之一。
13步骤 / 预期配对每步骤可带内联预期（可选）+ 用例级最终预期（可选）；启发式 + 导入预览纠错闸门兜底。
14优先级通用标志优先级仅解析末端叶子（用例），模块骨架不携带；叶子上两种写法：标题前缀 P0 · 或笔记专行 优先级: P0；多源优先级 标题>笔记>内建标记>未设；与《内容约定格式》自洽。
15UI 主题三套独立预设（不混合）：浅灰色（默认）/ 浅粉色 / 黑色；弱对比氛围 + 高对比文字（≥AA）；基于 AntD theme token 切换并本地持久化；自定义主题列为保留项。
